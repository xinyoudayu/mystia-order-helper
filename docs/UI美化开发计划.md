## 1 目标

**一句话：让 MOD 面板看起来像游戏自己的 UI，而不是一层贴上去的外挂。**

拆成四条可验收的标准：

| # | 目标 | 验收方式 |
|---|---|---|
| G1 | 面板质感贴合原版（和风纸条，不是 Unity 灰盒） | 截图对比原版订单小票 |
| G2 | 一眼扫完全场客人：谁在哪桌、什么状态 | 营业中 3 人以上时，不滚动就能看完列表 |
| G3 | 稀客能认出是谁（有立绘头像） | 稀客点单后头像显示真立绘，不变形、不挡字 |
| G4 | 推荐里的菜和酒"看得见"（有图标） | 每条推荐前带菜品/酒水图标（**批4，未做**） |

**两条硬约束（贯穿所有批次）**：

1. **零美术资源**——不打包任何图片，素材全部在游戏运行时从场景里抓。好处是不侵权、不增体积、游戏换皮 MOD 跟着变。
2. **不牺牲性能**——OnGUI 每帧跑两遍（§4.2），任何取图/拼串/`new` 都不许留在绘制路径上；素材一律在收集阶段（0.5 秒一次）缓存成自己的贴图。

### 批0 侦察（已完成）

**关键产出**（决定了后面所有批次的做法）：

```
订单卡 Order(Clone)/DampingFleld/MovingField/
├─ OrderBG_Normal    OrderReceipt_BG_0   32x66  border=(10,6,10,14)  ← 九宫格，面板底图就用它
├─ OrderBG_Current   OrderReceipt_BG_1   32x66
└─ ElementField/
   ├─ SpecialObject  （稀客）CharBG → Char(角色名Main_0,1) → Face(角色名Eyes_0,1) → CharFrame
   └─ NormalObject_* （常客）只有 Foods_N / Beverages_N 图标，没有人像
```

三条结论直接改变了原方案：

1. **常客没有头像**（游戏只给稀客做人像图层）→ 布局按"稀客头像列 / 常客图标列"分工。
2. **圆角和描边游戏自带**（`CharBG` 底衬 + `CharFrame` 描边，运行时染色）→ 不用自己做美术。
3. **所有图都是图集切片**（`packed`，2048² BC7）→ 不能整张贴，必须处理 UV（最终方案见 §4.5 的"拷副本"做法，绕开了 UV）。

### 批3.5 头像条（已完成）

用户要求：两个推荐框里也要能一眼看到是谁、并且方便点击切换。做法：

- **`DrawHintStrip`**：推荐框标题线下、内容区上方，**常驻一条头像**（48px，与主面板同款按钮），放不下自动换行；只有「还能点菜」的客人进条（已上菜等下一单的不进）。
- **不随内容滚动**：头像条独占一个独立 `BeginArea`，推荐列表在它下面的另一个区域滚动——锅开着的时候随时能点。
- **`FocusGuest`**：推荐框下方只展开「一位」客人的推荐（优先主面板选中的那位；他上车/离店就退回第一位稀客）。点头像 = 主面板和推荐框同时切过去，即用户说的「点头像跳转推荐」。
- `_activeGuests` 在采集阶段重建（0.5 秒一次），OnGUI 只读——不每帧 new List。
- 附带：`NoDrinkLine` 去掉重复的名字（标题行已经有），改成「没有匹配的酒水」；删掉不再使用的 `GuestDivider`。

**第二轮（用户验收后修正）**：

- **主面板也改成「顶部只排头像、不排文字」**：原来每行是「头像 + 两行文字」，文字把宽度吃光，一行只放得下一个头像。现在 `DrawAvatarRows` 只排头像、一行能排几个排几个（主面板默认 420 宽 → 7 个/行），点谁在下面展开谁的完整文字。
- **`DrawAvatarRows` 与 `DrawHintStrip` 共用同一套排布**（`StripPerRow` 算一行几个），三个面板的头像尺寸/高亮/换行规则一致。
- **头像取景修正**：`HeadCropRatio` 0.66 → 0.72，并新增 `HeadShiftDown = 0.18`，裁剪框从内容顶部往下挪一点——原来上沿死贴顶部、下沿正好切在眼睛下方，下巴和嘴全被切掉。
- **水平居中 bug**：原来把裁剪框中心夹在「内容左右边界」内，`side > 内容宽`时会把头像推到框子一侧；改为只夹「中心落在内容带上」，允许裁剪框超出内容。
- 顺手加了取景日志（前 8 个角色）：`取景 慧音 内容42x58 眼(ex,ey,ew,eh) 裁42@ox,oy`，以后调参数不用再靠截图猜。
- 删掉随列表行一起失效的死代码（`RowLine` / `MakeRow` / ListNameLine / ListStateLine）。

**第三轮：认不出的角色怎么办（人工映射兜底）**

自动匹配的前提是「立绘内部名里含显示名的字」。游戏一旦用代号、带编号前缀（`11_咲夜`）、
或日文异体写法，再多的别名表也猜不到（茨木华扇就是典型）。**不做 OCR、不做截图识图**，改用两层兜底：

- **`config\orderhelper-portraits.txt`（映射表）**：一行 `内部名 = 显示名`（如 `華扇 = 茨木华扇`），
  插件 Load 时读一次；查询顺序 `精确 → 映射表 → 别名 → 归一模糊`。改一行、存盘、重开游戏就生效，
  **不用改代码、不用重编译**。首次运行自动生成带注释的模板。
- **F11 列内部名**：把场上所有立绘的内部名导成 `config\orderhelper-portraits-keys.txt`，
  逐行标 `[有]` / `[缺]`。看到 `[缺] 華扇` 就知道该往映射表里填什么——**不需要用户截图，也不需要我看图认人**。
- 已有的 F10（`orderhelper-ui-samples\`）本来就是按内部名命名的 PNG，缺谁在她点单时按一下就有原图。

> 这两条的价值：把「识别失败」从「要改代码重发版」降级成「改一行配置」，以后任何新角色/DLC 角色
> 都不需要我再出包。截图手动配对作为最后手段保留，但正常流程用不到。

**第四轮：外部头像目录（优先级最高，玩家自己放图）**

玩家实测后提出更直接的办法：**自己截游戏里的头像、文件名改成人物名**。这条路比任何自动识别都可靠，
因为它完全是人工确认过的。实现：

- 目录 `config\orderhelper-portraits\`，放 `PNG/JPG`，**文件名 = 面板上显示的客人名**。
- 首次查询时懒加载（不在插件 `Load` 里读——那时渲染上下文可能没好），任意尺寸按中心裁正方形后缩到 48×48；
  本来就是 48×48 的直接拷像素，少一次重采样。
- **查询优先级最高**：外部图 → 精确命中 → 映射表 → 别名 → 归一模糊。外部图连别名都不用走。
- 文件名同时登记一份归一化名字，用户写成「茨木華扇」也能匹配「茨木华扇」。
- 目录里自动生成 `说明.txt`（要求、命名示例），玩家不用回来问。
- 顺带的好处：截图自带游戏的底衬和描边，比我们合成的更还原，也不会再出现「五官被头发挡住」这类取景问题。

**第五轮：官方素材包批量导入（40 张已装，53 张待认）**

游戏根目录自带 `东方夜雀食堂 头像&表情包 ~ Avatar Image`（本体 + DLC1–5 + DLCMUSIC，共 792 张，
每角色多个表情），画得比运行时抓的 64×64 立绘精细，但**文件名只有编号**（`本体/33-01.png`）。

- 工具链放在 `tools\`：`命名表.txt`（`目录/文件名 = 面板显示名`，值写 `?` 表示待定）→
  `import_portraits.py`（四角泛洪抠背景 → 裁到内容外框 → 补方形 → 缩 128 → 写进 `config\orderhelper-portraits\`）；
  `preview_portraits.py` 出效果预览，`make_todo_sheets.py` 出待认编号图。
- 本轮已确认 **40 个**（本体 23、DLC1 6、DLC2 4、DLC3 1、DLC4 4、DLC5 2），全部装进游戏目录。
- 还剩 **53 个**认不出（本体 12、DLC1 2、DLC2 5、DLC3 14、DLC4 5、DLC5 11、MUSIC 1）。
  原因：这批是像素风同人画，橙/三妖精/秦心/小铃/阿吽这类配角以及 PC-98 角色（艾伦、露易丝、魅魔、萨拉）
  的辨识特征被削弱，硬猜会张冠李戴——**认错比不认更糟**，所以这些先留空，由用户照 `_todo_*.png` 报名字，填一行表即可。
- 代码侧配套：外部目录查表加**双向包含**（`咲夜.png` ↔ 十六夜咲夜），避免译名长度不一致导致整批不生效。

## 3 批4：菜品与酒水图标（技术路径已查清）

### 3.1 已查到的事实（2026-10-23，程序集字符串搜索）

| 线索 | 含义 |
|---|---|
| `GetSellabeBGSprite_Public_Static_Sprite_Sellable_0` | **存在静态方法：传 `Sellable` 返回 `Sprite`** —— 最理想的正路 |
| `IngredientItemBadgeBeverageFoodCookerIzakayaSpriteAtlas` | 主图集，内含 Ingredient/Item/Badge/**Beverage**/**Food**/Cooker/Izakaya 全部图标 |
| `Dictionary_2_Int32_Sprite_0` | 有「int → Sprite」的字典，极可能就是 id→图标的映射 |
| `MultiLanguageSprite` | 酒水图标是多语言精灵（要取当前语言的那个） |
| 订单卡 sprite 名 `Foods_19` / `Beverages_6` | 命名疑似 `前缀_{id}`（DLC 菜为 `DLC1_Foods_1017`） |

### 3.2 两条候选路线

**路线 A（首选）：直接调 `GetSellableBGSprite(Sellable)`**
- 优点：不用猜编号，游戏自己给答案；`Sellable` 对象我们在推荐算法里已经有了。
- 风险：方法名里的 "BG" 暗示它可能是**背景图**而不是菜品图标，要先看一眼实际长什么样。
- 待确认：这个方法在哪个类上（字符串搜索只能看到签名，看不到归属类；需要 Mono.Cecil 或 dnSpy 确认）。

**路线 B（兜底）：按 `Foods_{id}` / `Beverages_{id}` 扫描场景 sprite**
- 复用批3 的扫描机制，改动小。
- 风险：要靠猜编号规则；菜品 400+，不可能每个都在当前场景里出现过（只有订单卡/料理面板里出现过的才有实例）→ **命中率低**。
- 更适合作为"路线 A 拿不到时，至少把常见菜显示出来"的补充。

### 3.3 执行顺序（开工时照这个走）

1. **先确认归属类**：用 Mono.Cecil 查 `GetSellabeBGSprite` 与 `IngredientItemBadgeBeverageFoodCookerIzakayaSpriteAtlas` 属于哪个类型。
   > 注意：本机 PowerShell 的 `Add-Type` 被安全策略挡住，**这条路走不通时要换工具**（dnSpy / ILSpy / 让用户手动跑）。已记进经验文档 §11.2。
2. **扩展 `UiProbe`**：导出几张菜品/酒水图标样例（`Foods_*`、`Beverages_*`），确认尺寸与是否带底衬（跟头像那批一样的做法——**先看图再写代码**）。
3. **决定路线**：A 能拿到就用 A；否则 B + 只缓存见过的。
4. **接入**：推荐条目前加图标列，图标缓存挂在 `DishCandidate` 上（收集阶段生成，OnGUI 只画）。
5. **降级**：拿不到图标就什么都不画（现状），不占位、不报错刷屏。

### 3.4 成本预估

| 项 | 估时 |
|---|---|
| 确认归属类 + 导出样例 | 0.5 天 |
| 取图与缓存（复用批3 机制） | 0.5 天 |
| 布局接入 + 装机验收 | 0.5 天 |
| **合计** | **约 1–1.5 天** |

风险点：如果 `GetSellableBGSprite` 拿不到（类的实例不好取），可能要退回"从图集按名字取"，成本 +0.5 天。

## 5 怎么验收每一批（固定流程）

1. **编译**：`powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1`
2. **装机**：游戏必须退出（dll 会被锁）；装完核对 `dist` 与游戏目录 dll 的 md5 一致。
3. **实机**：进营业 → 观察 → **截图**（AI 看截图判读，别只靠日志）。
4. **判据写死在批次里**（见 §2 每批的"验收方式"），不要凭感觉说"好了"。
5. **回滚**：出问题就把 `backup\recon-2026-10-23\MystiaOrderHelper-v1.5.2.dll` 拷回去（md5 `8A5B554D`）。
